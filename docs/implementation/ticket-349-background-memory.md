# #349 step 2 — background memory consolidation

Implementation scope: normal completion hook, graph-root completion, supported legacy completion, sidecar lifecycle and independent recovery. Step 1's wheel/cache evidence stays frozen. No first-token/pre-model preparation changes, UI redesign, commits or rollout in this slice.

## Implementation decisions

1. Persist the existing root completion/job synchronously. Replace inline model execution with a coalesced event notification. A single sidecar daemon reconstructs fresh official capabilities from durable ownership; it never retains a foreground host factory, agent, journal snapshot, cancellation token or RunBundle.
2. Persist a closed `pupu.memory-background-host.v1` record in the PuPu-owned `pupu_memory_background_hosts` table of the same context database. Exact keys: `schema`, `status`, `reason`, `provider`, `model_id`, `custom`. Credentials and custom transport configuration remain process-local in a bounded 128-owner cache. An authorized request refreshes these inputs. Restart can resolve built-in provider-specific environment keys; unavailable/custom credentials remain explicit retryable jobs, never silently route to a protocol twin or another provider's key.
3. A wake is only an in-process bit, not another queue or acknowledgement of execution. Recovery pages host registrations and queries existing pending/expired official jobs, then uses the official host's claim/lease/fence/reconciliation. Each genuine claim uses a fresh operation ID. A full bounded query page falls back to an official indexed claim rather than treating unobserved older work as absent. One job per owner per scan provides fairness.
4. Reconstruct context read scope from persisted ownership mappings (fail closed at the existing 10,000-lifecycle limit). Validate the actual claimed job's source generation before model execution and before each tool. Tools briefly acquire a separate owner-scoped cross-process file lock also taken by the host rebase API; ordinary chat never takes this lock, so background tools cannot reject a new foreground run. Model I/O holds neither this lock nor a session guard. A busy rebase causes a background retry. Official deletion/tombstone and lease/CAS protections remain in force. Stop has its own token checked before tools, and a bounded join.
5. Background results remain in job/review storage and content-free logs. Foreground receipts remain pending/no-worker-receipt and are never mutated later. Existing explicit/manual worker API remains stable; the dispatcher does not reuse its per-root cached idle/retry receipts.
6. Legacy jobs retain their own stored model and configuration fingerprint; only narrow provider/configuration inputs are retained transiently. No asynchronous callback appends to foreground diagnostics.
