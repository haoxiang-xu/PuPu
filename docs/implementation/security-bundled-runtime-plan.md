# Bundled MCP runtime security refresh

Refresh the independently redistributed MCP toolchain, including nested copies that the application's npm and Python requirement audits do not inspect. This candidate depends on the dependency/extractor and curated MCP SDK security candidates; it does not merge their source changes into this branch.

## Scope and implementation

- Preserve the supported target set, Node 24 LTS, CPython 3.12 ABI, launcher paths, system certificate/proxy policy, and immutable archive provenance.
- Pin Node 24.22.1, uv 0.13.4, CPython 3.12.15+20261021, and bootstrap certifi 2026.10.19 using primary upstream SHA-256 metadata and independently downloaded bytes for all four targets.
- Node's archive still includes vulnerable nested npm packages. Replace the whole npm package with maintained npm 11.21.1 and its compatible whole ip-address dependency with 10.7.4, retaining npm/npx launchers and all licenses.
- Official pip 26.2.2 still vendors urllib3 2.7.0. Replace only that complete vendored package using official urllib3 2.8.0, retaining pip's established namespace and optional Brotli conventions. Update the installed package and the immutable-base ensurepip wheel together; retain PBS-specific distlib launchers. Regenerate RECORD, vendor inventory, CycloneDX component, attribution, and deterministic wheel ZIP. Do not remove pip/ensurepip or modify urllib3's security algorithms.
- Accept only closed, typed curation descriptors. Download and verify all immutable source bytes before mutation. Reject an unexpected base package, base wheel, package tree, malformed archive, unsafe path/symlink ancestor, or receipt. Curate only the private temporary stage before sealing and computing tree identity. Validate the complete stage before replacing a previously valid stage.
- Preserve the raw upstream runtime archive digest and add a separate curation receipt with exact package sources, versions and digests. The existing staged-tree identity rotates managed npm/uv caches when the curated payload changes. Third-party notices must include the replacement npm Artistic-2.0 license and complete bundled license/source attribution.

## Boundary contracts

- **BC-001 — upstream archive to staged runtime:** immutable HTTPS archive identity, target layout, executable command and required files must match pins. Curation may replace only its typed, derived package destinations; a malformed or mismatched input leaves the prior stage unchanged.
- **BC-002 — pip vendoring to installed/bootstrapped environments:** installed pip and ensurepip must both expose urllib3 2.8.0 through `pip._vendor`; base pip remains 26.2.2. Namespace transforms preserve idna and emscripten binding semantics, existing optional Brotli policy, PBS distlib launchers, licenses and valid RECORD entries. A deterministic local curation receipt distinguishes the downstream wheel from the upstream wheel without misrepresenting its source digest.
- **BC-003 — stage to Electron/sidecar consumers:** manifest command/argument and environment contracts remain unchanged. `staged_tree_sha256` includes curation and receipt, maintaining existing cache separation. Package verification and third-party license gates require the expected curation evidence before packaging. No new UI or provider behavior is introduced.
- **BC-003 Windows signing invariant:** Authenticode may change the outer Node executable, so Windows packaging deliberately skips its whole-runtime checksum. The closed Node curation receipt separately requires a valid `npm_tree_sha256`, covering the complete npm/ip-address JavaScript and license subtree, and the verifier always checks it even when the outer checksum is disabled. Executable signing remains permitted; package source mutations, a missing digest or an invalid digest fail before packaging (AC-002).
- **BC-004 — cross-candidate deployment:** acceptance uses this staged runtime with the dependency/extractor and curated MCP SDK candidates, preserving their exact artifact identities. Native Windows/Linux CLI execution remains a release-platform gate; cross-platform archive staging alone is not native acceptance.

Admission and identity are explicit. BC-001 uses **VERSIONED** upstream archive pins (source URL, archive digest, target and runtime version) and **CLOSED** typed curation descriptors: only Node `schema_version/npm/ip_address` or Python `schema_version/pip/urllib3`, with exact source key sets and no caller-selected destination or transform. BC-002 projects those exact sources into pip's existing private import namespace; the canonical receipt is **CLOSED**, recording the upstream wheel identities separately from the derived wheel and vendor-tree digests. Unexpected base bytes or metadata reject the stage without fallback to old vulnerable packages. BC-003 retains the existing **VERSIONED** schema-1 runtime manifest and additive optional runtime fields; the stager/verifier binds pins digest, commands, archive identity, staged tree and curation receipt digest before the sidecar consumes its unchanged command/environment representation. Unknown curation or receipt fields fail; existing unrelated manifest extensions retain their prior policy. These boundaries map to AC-001/002/003. BC-004 maps to AC-004 and the combined candidate report, and retains the exact Unchain wheel and imported runtime protocol manifest identities from the [Python dependency plan](security-python-dependencies-plan.md); those must not be rebuilt or replaced during acceptance.

## Sequence and acceptance

- **SEQ-001:** verify pins/source hashes → extract into private temporary stage → validate base identities and safe destinations → replace complete packages → update inventory/RECORD/licenses/receipt → validate full stage → seal/checksum → atomically publish. Any failure before publish preserves the previous stage.
- **SEQ-002:** installed Python invokes pip; a fresh venv invokes ensurepip; uv/uvx installs and runs a safe PEP 517 fixture with the exact bundled Python. Both bootstrapping paths must retain the same patched vendor and certificate policy.

State applicability: first/second normal chat messages, first/second interaction, durable chat resume/replay, and normal/graph/subagent provider execution are **NOT_APPLICABLE** to the changed producer/consumer paths: this candidate executes only at build-time staging or managed local MCP package bootstrap and does not alter chat persistence, provider projection, or the runtime protocol. Package repeat/retry and failed-stage rollback apply to SEQ-001/BC-001 and AC-002; fresh process/venv bootstrap and independent managed cache identity apply to SEQ-002/BC-002/003 and AC-003. Existing managed-runtime backend tests cover cache identity separation, and actual ensurepip/uvx controls run fresh environments. Native Windows/Linux execution and exact combined deployed artifact acceptance remain **NOT_RUN/PENDING**, so active rollout remains **INCOMPLETE** until the combined/platform gates pass. No model run is claimed or required by this build-time change.
- **AC-001:** actual archive hash verification, complete staging and integrity verification for darwin-arm64, darwin-x64, win32-x64, linux-x64. Audit the actual nested npm inventory on all four targets; verify installed and ensurepip inventories and receipts independently.
- **AC-002:** negative tests cover corrupt hash/archive, unexpected base version/tree, unknown curation fields, unsafe destination ancestors, receipt mismatch, deterministic wheel/RECORD correctness, and failure preserving a prior stage. Windows afterPack controls preserve executable signing while rejecting npm and ip-address source mutations and missing/invalid subtree digests. Positive controls cover npm/npx, pip offline wheel install, ensurepip in a new venv, uv/uvx and a safe local PEP 517 project.
- **AC-003:** run owning staging, packaging, notices and backend managed-runtime/TLS tests under the isolated patched Node. Run actual host native packaged-runtime smoke without GUI, model or provider inference. Preserve exact command/results and platform limitations in managed security evidence.
- **AC-004:** fresh independent review, source diff review, current GitNexus reindex and complete non-partial/non-truncated `detect_changes --scope all` before delivery. No host-global upgrades and no commit in the original checkout.

## Evidence status

Primary sources and immutable archive evidence are retained in the managed security artifact collection under `artifacts/runtime-binaries/`. All four actual upstream archive combinations have passed complete curated staging, sealed-tree/receipt verification and third-party notice collection (eight entries per target). Each actual npm inventory contains 142 packages and has zero current registry advisory matches. The installed pip and ensurepip inventories match across all targets; urllib3 is 2.8.0. Pip's remaining six advisory alias records concern absent setuptools PackageIndex/FileList code and absent native msgpack extension code, with actual shipped-file evidence; those are documented as not applicable, not falsely described as patched packages.

The curated ensurepip wheel is identical across all targets: SHA-256 `260811865d874b11377d7584d9be8fbce8b1a6c70ba6466ba3ea0f91ad25fb42`. Every member's ZIP CRC and RECORD SHA-256/length was independently checked with Python's standard library; all ZIP timestamps are 1980-01-01. Installed urllib3 source/license bytes match that wheel. Windows PBS-derived urllib3 bytecode is removed with the replaced directory only after all source/license bytes match the official pip base wheel; PBS-specific distlib launchers remain unchanged.

Owning staging/packaging/notices/curation tests passed: 38 tests under isolated Node 24.22.1. Backend managed-runtime/TLS tests passed: 54 tests and 11 subtests. Actual native darwin-arm64 acceptance passed for Node 24.22.1, npm/npx 11.21.1, uv 0.13.4, CPython 3.12.15, pip 26.2.2 with vendored urllib3 2.8.0, Unicode IDNA, and system-trust bootstrap. Positive controls include npx running an offline local CLI, pip installing an offline wheel, a fresh venv bootstrapping the curated wheel with ensurepip and installing/importing its own wheel, and uvx building/running a safe offline PEP 517 local CLI. Native packaged-runtime smoke also passed. No GUI, model or provider inference was used, and no sidecar Python source was changed by this candidate.

Follow-up Windows receipt regression was reproduced before the fix using a private copy of the actual Windows stage: with the signing exception active, both an executable trailer and an unauthorized npm source edit were previously accepted. The new production afterPack regression fails on that prior implementation and distinguishes permitted executable changes from rejected npm/ip-address changes, missing digests, malformed digests and non-string digests. The follow-up focused suite passes 39 tests. It adds only a receipt subtree digest and strict verification; package source bytes and the deterministic pip wheel are unchanged. Its refreshed stages and final check results supersede the initial stage/receipt identities above in the managed Windows-fix evidence.

Fresh independent review and final graph evidence are delivery gates. Native Windows/Linux execution and the combined security candidates' full package/license checks remain platform/integration acceptance; cross-target staging and the host controls above do not substitute for those checks.
