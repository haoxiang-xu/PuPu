# v0.1.13 release external-network retry plan

## Goal

Reduce false release failures caused by short-lived external service or network interruptions without retrying mutations that can publish twice, duplicate work, or operate on partially modified artifacts.

## Boundary contracts

### BC-001 — Apple notarization ticket reads

- Boundary: PuPu release runner -> Apple notarization/stapling service.
- Request identity: the exact packaged `.app` produced by the candidate build.
- Response: successful stapler validation for that unchanged application bundle.
- Retryable: Apple ticket-delivery/CloudKit network timeout, DNS/connectivity loss, connection reset, HTTP 429, and HTTP 5xx.
- Not retryable: credentials, keychain, certificate, signature, rejected notarization, or missing-ticket failures.
- Compatibility invariant: retrying validation must not rebuild or modify the candidate.

SEQ-001: attempt -> classify failure -> bounded wait -> retry the same read -> succeed or fail closed after the configured maximum.

- AC-001: the observed `NSURLErrorDomain Code=-1005` CloudKit failure is retried.
- AC-002: credential and signature failures stop after one attempt.
- AC-003: repeated transient failures fail after at most three attempts.

### BC-002 — GitHub release metadata and artifact reads

- Boundary: PuPu release runner -> GitHub REST API / Actions artifact download / Release asset download.
- Request identity: repository, run ID or release tag, artifact name/pattern, and destination path remain unchanged across attempts.
- Response: exact metadata bytes on stdout or complete artifact bytes at the declared destination.
- Retryable: connection reset/timeout, temporary name-resolution/connectivity failure, HTTP 429, and HTTP 5xx.
- Not retryable: authentication/authorization failures, not found, validation errors, and provenance failures.
- Partial output rule: a declared download destination is removed before a retry; cleanup is restricted to a relative path below the current working directory.
- Stream rule: command stdout remains byte-for-byte pipeable; retry diagnostics go to stderr.

SEQ-002: attempt -> classify failure -> remove only the declared partial destination -> bounded wait -> repeat the same read -> succeed or fail closed.

- AC-004: GitHub 502 and connection-reset failures are retried.
- AC-005: GitHub 401, 403, and 404 failures stop after one attempt.
- AC-006: unsafe cleanup targets are rejected before the command runs.

### BC-003 — npm and pip dependency registries

- Boundary: release runner package manager -> configured npm/Python package registry.
- Request identity: lockfile and requirements remain unchanged.
- Response: the same dependency set selected by `npm ci` or the requirements file.
- Retry policy: use the package manager's built-in bounded fetch retries and extended per-request timeouts.
- Compatibility invariant: retries may fetch bytes again but must not change dependency selection.

SEQ-003: package manager fetch -> built-in transient retry/backoff -> deterministic install or failure.

- AC-007: release workflows use explicit npm fetch-retry limits.
- AC-008: network-backed pip installs use explicit retry and timeout limits.

### BC-004 — excluded mutation boundaries

The following are intentionally not wrapped in automatic retry:

- GitHub Release create/edit/upload and final publish operations.
- GitHub workflow dispatch or operator command mutations.
- Azure Artifact Signing actions and any operation that mutates signed files.
- Provenance, signature, hash, or policy verification failures.

These operations require reconciliation or a fresh pristine input before retry. A generic retry could duplicate publication, hide an authorization failure, or sign a partially modified payload.

- AC-009: workflow contract tests reject generic retry wrappers around release mutations and Azure signing.

## Verification

The exact deployed pair is the workflow YAML plus the retry helper from the same immutable PuPu tag. Verification requires:

1. focused retry helper and workflow contract tests;
2. the complete `npm run test:release-qa` suite;
3. JavaScript syntax and whitespace checks;
4. GitNexus change detection before commit;
5. a fresh candidate run from a recreated immutable release tag after merge.
