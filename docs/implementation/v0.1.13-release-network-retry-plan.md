# v0.1.13 release external-network retry plan

## Goal

Reduce false release failures caused by short-lived external service or network interruptions without retrying mutations that can publish twice, duplicate work, or operate on partially modified artifacts.

## Boundary contracts

### BC-001 — Apple notarization ticket reads

- Boundary: PuPu release runner -> Apple notarization/stapling service.
- Request identity: the exact packaged `.app` produced by the candidate build.
- Response: successful stapler validation for that unchanged application bundle.
- Retryable: Apple ticket-delivery/CloudKit network timeout, DNS/connectivity loss, connection reset, HTTP 429, and HTTP 5xx.
- Not retryable: credentials, keychain, certificate, signature, rejected notarization, or missing-ticket failures.
- Compatibility invariant: retrying validation must not rebuild or modify the candidate.

SEQ-001: attempt -> classify failure -> bounded wait -> retry the same read -> succeed or fail closed after the configured maximum.

- AC-001: the observed `NSURLErrorDomain Code=-1005` CloudKit failure is retried.
- AC-002: credential and signature failures stop after one attempt.
- AC-003: repeated transient failures fail after at most three attempts.

### BC-002 — GitHub release metadata and artifact reads

- Boundary: PuPu release runner -> GitHub REST API / Actions artifact download / Release asset download.
- Request identity: repository, run ID or release tag, artifact name/pattern, and destination path remain unchanged across attempts.
- Response: exact metadata bytes on stdout or complete artifact bytes at the declared destination.
- Retryable: connection reset/timeout, temporary name-resolution/connectivity failure, HTTP 429, and HTTP 5xx.
- Not retryable: authentication/authorization failures, not found, validation errors, and provenance failures.
- Partial output rule: a declared download destination is removed before a retry; cleanup is restricted to a relative path below the current working directory.
- Admission: CLOSED retry policy; only the configured read profiles and transient error patterns are admitted. Metadata schema/provenance validation still runs independently after transport succeeds.
- Stream rule: stdout is committed byte-for-byte only after one attempt succeeds. Failed-attempt bodies are discarded; retry diagnostics and command stderr remain on stderr. Exhaustion leaves stdout empty. Buffering is capped at 16 MiB and overflow fails closed.

SEQ-002: attempt -> classify failure -> remove only the declared partial destination -> bounded wait -> repeat the same read -> succeed or fail closed.

- AC-004: GitHub 502 and connection-reset failures are retried.
- AC-005: GitHub 401, 403, and 404 failures stop after one attempt.
- AC-006: unsafe cleanup targets are rejected before the command runs.
- AC-010: real `gh api` against a local 502-then-200 service emits exactly one successful JSON body accepted by the strict JSON consumer; persistent 502 responses leave stdout empty and exit nonzero.
- AC-011: each macOS/Windows restart and Windows diagnostic consumer resolves to the same directory as the artifact downloader and its retry cleanup target.
- AC-012: the README workflow invokes the helper from its frozen `release-tools` checkout, independently of the older `main` content being edited.

### BC-003 — npm and pip dependency registries

- Boundary: release runner package manager -> configured npm/Python package registry.
- Request identity: lockfile and requirements remain unchanged.
- Response: the same dependency set selected by `npm ci` or the requirements file.
- Retry policy: use the package manager's built-in bounded fetch retries and extended per-request timeouts. Historical `fixture-source` checkouts receive explicit npm command flags because the current tag's `.npmrc` is not present in those older sources.
- Compatibility invariant: retries may fetch bytes again but must not change dependency selection.

SEQ-003: package manager fetch -> built-in transient retry/backoff -> deterministic install or failure.

- AC-007: release workflows use explicit npm fetch-retry limits.
- AC-008: network-backed pip installs use explicit retry and timeout limits.

### BC-004 — excluded mutation boundaries

The following are intentionally not wrapped in automatic retry:

- GitHub Release create/edit/upload and final publish operations.
- GitHub workflow dispatch or operator command mutations.
- Azure Artifact Signing actions and any operation that mutates signed files.
- Provenance, signature, hash, or policy verification failures.

These operations require reconciliation or a fresh pristine input before retry. A generic retry could duplicate publication, hide an authorization failure, or sign a partially modified payload.

- AC-009: workflow contract tests reject generic retry wrappers around release mutations and Azure signing.

### BC-005 — build-process output to Apple retry classification

- Producer: stdout/stderr emitted by the signed macOS build child process; consumer: the Apple profile used by `runMacReleaseBuildWithRetry` and standalone Apple ticket reads.
- Shape/canonical representation: bounded text with mixed successful build diagnostics and the final error; classification remains a boolean, with the original exit status propagated on rejection/exhaustion. CLI arguments and result schema do not change.
- Admission: CLOSED. An explicit Apple operation context plus an allowlisted transient network signature is required. Apple-specific permanent authentication, signing, certificate, missing-ticket, rejected/Invalid notarization, and stapler code-65 signatures still veto a retry, in either order relative to the timeout.
- Projection: benign optional-import `not found`, normal `keychain=` fields, and successful keychain-unlock diagnostics are not permanent signing failures. GitHub/git profiles retain the original permanent-error policy unchanged. Unknown errors without positive transient evidence still fail closed.
- Identity: workflow plus both retry helpers must come from the same frozen PuPu revision. The build command, version, feature snapshot, Unchain wheel SHA-256 and manifest identity stay unchanged between attempts. No runtime API or Unchain source is changed by this follow-up.
- Failure semantics: full-build recovery retains the existing two-attempt/30-second-delay limit and removes only generated `dist` before rebuilding. Ticket-validation reads retain their existing bounded policy and do not mutate the app. A failed or partial package is never admitted as a release candidate.

SEQ-004 (BC-005): pristine invocation -> noisy build output -> Apple timeout -> classify -> clean generated `dist` only -> bounded wait -> identical command -> success, or original nonzero status after exhaustion. Permanent-error and unknown-error branches stop after the first attempt without cleanup or waiting. Retry state is process-local; independent invocations start fresh. Chat interaction, durable resume and sidecar restart cells are N/A because these helpers run only in the release runner, outside the app/runtime lifecycle.

- AC-013: sanitized observed PyInstaller diagnostics plus the actual notary timeout shape classify as retryable; successful signing/keychain diagnostics cannot suppress it.
- AC-014: a real spawned Node build fixture emits the noisy failure, creates partial `dist`, then succeeds on attempt two only if the stale output was removed; an unrelated working-directory marker survives.
- AC-015: repeated noisy timeouts stop at two attempts with the nonzero build status; genuine permanent errors mixed with a timeout in either order do not retry. GitHub/git permanent-error precedence remains unchanged.
- AC-016: retain red-before-green evidence and run the complete release-QA/harness suite plus independent review. Signed deployment of the corrected helper remains NOT_RUN until it is merged and explicitly selected for a later immutable workflow execution; the current manual retry is not that evidence.

### BC-006 — command-scoped Intel runner transport

- Producer: the frozen workflow invokes `macos-intel-tcp.mjs -- command [args...]`; consumer: the same signed build or ticket/evidence verifier, executed with its original arguments, environment, working directory, credentials, and exit status.
- Boundary: command process -> macOS PF -> Apple HTTPS transport. Admission is CLOSED for privilege activation: Darwin/x64, GitHub Actions, GitHub-hosted runner, repository `haoxiang-xu/PuPu`, numeric run ID and attempt. Other platforms/local invocations pass through without privileged network changes.
- Canonical representation is an argument vector, not shell interpolation. The transport rule is the fixed `block return out quick proto udp from any to any port 443`. It lives only in a unique child of the already evaluated `com.apple/*` parent; missing parent, failed rule readback or missing enable token fails before the command starts.
- The helper releases only its own PF enable reference and flushes only its own anchor. It must not overwrite the root ruleset, disable PF globally, flush states, weaken TLS, or skip codesign/notary/stapler/Gatekeeper checks. Setup and cleanup failures remain nonzero. No signing material or full environment is logged.
- Identity: helper and workflow come from the same frozen PuPu commit; historical fixture builds invoke the helper from the current frozen tools checkout, not the N-1 source. Signed Candidate build, standalone stapler verification, signed N-1 fixture build/evidence and standalone signing qualification all use it. ARM64 remains a no-op at the privilege boundary.
- Deployment evidence must still be the exact PuPu Candidate + its one reused Unchain wheel and manifest. The TCP diagnostic is supporting transport evidence only. A fresh Candidate is required after selecting the merged correction; the failed old run cannot be promoted.

SEQ-005 (BC-006): guard -> unique anchor -> load rule -> acquire own enable token -> verify readback -> original command -> cleanup anchor and token -> propagate result. Repeat invocations use separate anchors. Command failure, thrown/spawn failure and handled SIGINT/SIGTERM run cleanup; cancellation propagates to the child process group and cannot trigger a retry afterward. SIGKILL/host loss cannot execute userspace cleanup; activation is therefore limited to disposable GitHub-hosted runners. No durable app/chat state is involved; chat interaction, sidecar restart and replay cells are N/A.

- AC-017: hosted Intel activates scoped PF; ARM64, Linux, Windows and local Intel never invoke PF. Invalid activation identity fails closed before the child.
- AC-018: missing parent/token, PF load/verify failure and cleanup failure cannot become success; original command failures remain failures; exact own anchor/token cleanup occurs on every reachable exit.
- AC-019: SIGINT/SIGTERM terminate the command group, clean up and return cancellation status. Local tests use strict injected PF responses and harmless child fixtures, never actual PF or signing credentials.
- AC-020: workflow contracts cover Candidate build and later stapler verification, N-1 fixture build/evidence and standalone signing qualification; original signature/provenance enforcement stays intact.
- AC-021: focused red-before-green tests, complete release-QA + harness tests, complete raw graph change checks and independent review precede commit/merge. Actual signed PuPu Intel acceptance remains NOT_RUN until the new immutable Candidate executes.
