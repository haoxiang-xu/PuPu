## Cause and scope

Azure signed both the payload and installer successfully. The shared signing
action then tried to execute `app-builder-bin/win/x64/app-builder.exe`, which
is absent from the locked Electron Builder 26.15.3 dependency set. The locked
builder itself now uses the pure JavaScript `buildBlockMap` producer from
`app-builder-lib/out/targets/blockmap/blockmap.js`.

Replace that single obsolete command in the shared action. It is used by the
Candidate, standalone signing qualification, Windows restart-update fixture
and upgrade diagnostic. Keep signing, native verification, runtime admission,
version/source selection and the existing updater metadata validator intact.
Do not add or downgrade dependencies.

The original Candidate and tag remain unchanged. This patch alone does not
authorize a retry, artifact deletion, tag recreation or publication.

## BC-001 — signed installer to external blockmap and update metadata

Producer: Azure-signed NSIS installer bytes, then the locked builder's real
`buildBlockMap(inFile, "gzip", outFile)` implementation. Consumer: the external
`.exe.blockmap`, existing `refreshWindowsUpdaterMetadata`, and the Windows
updater's differential download/installer verification.

Transport: filesystem artifacts and the shared action's Node CLI. CLI admission
is CLOSED: exactly one nonempty `--installer` argument. The output is always the
separate `<installer>.blockmap`; callers cannot choose append mode or overwrite
the input. The producer's omitted/empty third argument appends to the input and
would invalidate Authenticode, so it must never be used here.

Build into a fresh sibling temporary directory, verify the input SHA-512 and
size before/after generation and against producer metadata, then atomically
replace the destination. This also replaces a stale destination file/link
without following it into the installer. Always remove temporary output.
Failure must propagate before updater metadata refresh or signing evidence.

Canonical external format: gzip-compressed blockmap JSON v2, one file at offset
zero, parallel checksum/size arrays whose sizes sum to the original installer
length. Existing `latest.yml` primary/file records continue to describe the
signed installer SHA-512 and size. No schema or unknown-field policy in that
existing metadata consumer changes.

Artifact identity: preserve the exact signed installer bytes; retain its
blockmap and refreshed metadata in the future Candidate's own manifest.
Runtime protocol admission is unchanged. A future package/Qualification run
must still bind its own retained Unchain wheel and actual runtime manifest;
local fixture tests cannot certify a Windows signature or a sealed Candidate.

AC-001: reproduce the obsolete path failure with the actual locked dependency
set, then use the real new CLI/producer on bounded multi-chunk fixture bytes in
a path containing spaces and Unicode. Strictly inspect decompressed blockmap
shape/chunk coverage and independently compare installer bytes/hash/size.

AC-002: generate again and replace a stale blockmap deterministically. An output
hardlink to the installer is replaced without changing input bytes.

AC-003: missing/invalid CLI input and an output directory collision fail nonzero;
installer and metadata remain unchanged, and temporary files are cleaned.

AC-004: follow the actual composite action's Node command order through new
blockmap generation and existing metadata refresh. Verify SHA-512/size describe
the fixture's unchanged bytes. Exercise the generator CLI's failure exit and
unchanged metadata separately; statically verify the actual PowerShell guard
throws on a nonzero generator exit before the metadata command. Keep
shared-action parity for all four callers. Actual PowerShell failure-branch
execution is NOT_RUN on this host, which has no `pwsh`; the extracted Node
commands' success test does not execute or simulate that shell branch.

## SEQ-001 — post-sign transition and repeat

Identity: installer path, original signed byte hash/size, sibling blockmap path
and corresponding `latest.yml` record. Start with an old unsigned blockmap and
metadata. Azure produces signed bytes; generate into a fresh separate output;
verify unchanged installer; replace the blockmap; refresh metadata from signed
bytes; continue the existing native signature/evidence checks. Repeat generation
on the same input yields identical output. A missing input or failed output
replacement stops before metadata refresh. Maps to BC-001 and AC-001–004.

Chat/interaction/resume/sidecar-restart matrices are NOT_APPLICABLE to this
tool-only patch: no application/runtime code, persistence schema or protocol
changes. Native Windows signed-package and restart-update checks are PENDING
for the corrected release pipeline; no local certificate/provider/app/model run
is required or claimed by the fixture tests.
