# #349 缓存阶段收尾报告（2026-09-26）

**这一小步的本地验证和性能统计已完成。Memory V3 整张 ticket 仍在进行中。**

本次没有再改生产逻辑，主要补齐了对照测试、数据库统计、内存测量，以及固定版本的复测材料。

## 实际节省多少

同一个固定运行库、Python 3.12.11，每组先预热 10 次，再测量 100 次。下表只计算「准备下一次模型上下文」，不包含工具执行、保存工具结果、网络、模型生成或 streaming 时间。

| 历史长度 | 场景 | 关闭缓存 | 开启缓存 | 节省时间 |
|---|---|---:|---:|---:|
| 1 轮 | 历史没变化 | 6.22 ms | 8.19 ms | **慢 1.97 ms** |
| 1 轮 | 工具结果已保存，继续模型调用 | 12.38 ms | 14.57 ms | **慢 2.19 ms** |
| 25 轮 | 历史没变化 | 76.23 ms | 51.21 ms | 25.02 ms（32.8%） |
| 25 轮 | 工具结果已保存，继续模型调用 | 83.51 ms | 72.33 ms | 11.18 ms（13.4%） |
| 100 轮 | 历史没变化 | 298.63 ms | 181.91 ms | 116.72 ms（39.1%） |
| 100 轮 | 工具结果已保存，继续模型调用 | 299.18 ms | 250.76 ms | 48.41 ms（16.2%） |

这些是中位数。25/100 轮场景的 p95 也改善了；100 轮工具续跑的 p95 从 343.48 ms 降到 282.10 ms。1 轮场景的中位数和 p95 都变慢，原因是新增的完整性检查在短历史下比省下的读取更贵。本次保留并记录约 2 ms 的开销，没有另加自动切换策略。

因此，这项优化在长会话里有帮助，但它不会消除整条链路里数秒的等待，也没有改变之前约 10 秒的模型请求阶段。

## 数据库到底少做了什么

每次准备上下文，重复读取完整历史从 **2 次降到 0 次**，改为检查已有缓存、读取新增事件。

但要区分三件事：

- **返回的数据量明显减少。** 100 轮工具续跑中，SQL 返回的数据从约 526 KB 降到 6.4 KB，减少约 98.8%。
- **长历史下，查询语句也减少。** 同一场景的 SELECT 从 413 次降到 21 次。
- **读取事务反而增加。** 完整性检查使每次上下文构建的读取事务从 4 次变成 8 次。缓存并没有让数据库完全退出这条路径。

写入没有作为优化对象。工具调用和结果仍然要保存；工具结果之后的上下文记录写入也保持 1 个写事务、2 条写语句。缓存不能把未保存的结果当作已保存的历史。

这里的“数据量”是 SQLite 返回给 Python 的逻辑数据字节，不是硬盘实际读写量。

## 内存和正确性

100 轮、带工具结果的样本中，缓存快照序列化后约 **190 KiB**；重新建立缓存后新增且仍保留的 Python 内存约 **0.54 MiB**，建立过程峰值约 **1.47 MiB**。这不是整个应用的内存占用，也不是最大负载测试。32 MiB 的配置上限限制的是序列化快照，不能理解成 Python 实际占用的硬上限。

最终使用固定运行库完成：

- **1,499 项核心及对照测试通过**；原有 1 项跳过、1 项预期失败保持不变。
- **195 项 PuPu 侧测试通过**，覆盖存储兼容、恢复、Graph 入口和协议检查等。
- 缓存开关的完整上下文、消息、摘要标识和事件顺序对照通过，覆盖工具续跑、连续审批、会话恢复、缓存清空、重新打开数据库、子任务和超过 128 KB 的工具结果。
- OpenAI、Anthropic、Gemini、Ollama、Hyperspace 五种 provider，在工具调用前后生成的请求字节完全一致。这些是本地协议测试，没有发送真实模型请求。
