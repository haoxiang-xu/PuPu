# 第二步：把记忆整理放到后台

**实现完成，本地验证通过。** #349 保持进行中；尚未做正式功能验收或切换日常应用。

现在的流程是：回复完成 → 可靠保存记录和记忆任务 → 本轮结束。后台再独立整理记忆。因此，记忆整理变慢时，不会要求本轮继续等它，也不会占住下一条普通聊天的执行锁。

普通会话、Graph 根任务和旧路径都已接入。Tool call 和工具结果仍然完整保存，任务领取、重试和防重复写入机制仍然保留。后台结果独立保存，不会回头修改已经结束的回复。

已经验证：

- **247 项测试通过，另有 65 项子检查通过。**
- 故意卡住记忆模型时，本轮可以结束，同一会话的下一条消息也可以进入处理。
- 重复通知不会重复写入；服务重启后能恢复任务；过期租约可以重新领取。
- 会话删除、重置或服务停止后，旧后台任务不能继续写回记忆。
- 重启后缺少密钥或原配置时，任务明确保持待重试，不擅自切换服务商。
- 使用固定代码和上一阶段同一个运行库，实际启动、停止并重启了独立测试服务，两次均正常。

这一步省掉的是**回复结束后等待记忆整理的时间**。前面的约 6 秒准备工作和主模型响应时间属于后续步骤；目前还没有新的整轮耗时实测。

改动保存在 #349 的独立工作区，没有切换你日常使用的应用。安装包验收和正式启用仍待后续完成。
