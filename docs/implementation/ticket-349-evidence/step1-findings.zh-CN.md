## 可以确认的耗时原因

1. **每次被测的模型上下文构建都完整读取了两遍执行历史。**请求工厂在 `unchain/src/unchain/context/request_factory.py` 的 `_validated_snapshot` 读取一次；协调器在 `unchain/src/unchain/context/coordinator.py` 的 `compile` 再读取一次。SQLite 的快照操作会读取该次执行的历史事件。工具续接也是如此；即使同一执行已经预热，重复构建时仍会做这些工作。
2. **本地准备时间随历史长度显著增加。**普通消息在 1、25、100 轮测试中的中位数分别为 6.58、78.33、303.97 毫秒。100 轮时，读取历史约占 304 毫秒总耗时中的 87 毫秒。只减少一次 SQLite 读取，仍不能消除其余的校验和消息整理时间。单独的 cProfile 结果（`profile-step1.txt`）从调用热点上印证了重复的 JSON 资源校验和标准消息投影；性能分析器会放大耗时，因此其中的时间数字不能当作基准数据。
3. **Memory Agent 执行可能延后前台的“本轮完成”。**`PupuMemoryAgentWorkerModule.configure` 安装的 `process_after_enqueue` 回调会同步调用 `process_next`；图根节点和旧版完成路径也会在当前流程中直接运行它。在受控实验中，给工作任务增加 250 毫秒延迟，工作回调的中位数增加了约 255 毫秒，而任务入队本身仍只需约 0.002 毫秒。这证明了该路径存在同步等待关系；它**不证明**每次打招呼都会启动 Memory Agent，也不证明截图中 18.4 秒花在了这里。

## 目前不能归因的时间，以及下一条测量边界

本次基准只测量本地上下文准备和受控的完成回调。它**没有**测量 Electron/IPC、请求进入服务端的处理、辅助进程冷启动、模型服务的网络和输入处理、首个可见字出现的时间、输出速度、真实 Memory Agent 模型延迟，或真实用户消息和媒体的大小。因此，不能用这些数据拆分截图中的 18.4 秒。截图显示约 1.59 万个输入 token，模型处理输入可能是耗时来源之一，但必须取得模型服务相关时间点才能验证。基准数据中的 `provider_calls: 0` 只表示这个模拟测试没有调用模型服务，不能当作生产环境中“没有额外模型调用”的证据。

下一阶段应针对**同一个 run ID**，只记录时间点而不记录内容：请求进入、首次发给模型、首个可见字、工具结果写入、再次发给模型、主任务完成状态写入、记忆任务入队、后台工作开始和结束、以及前台显示完成。分别比较一句简短问候、同一对话的第二条消息、长历史对话和确实有记忆候选内容的一轮。在拿到这些数据之前，只能把上述两处视为已测到的本地耗时来源；18.4 秒中的其余时间仍未定位。
