## Design and existing integration

This follows the native graph core checkpoint, not a redefinition of the accepted #341 panel/drill slice. The product direction main storyline is Agent building/validation/export. First make a new Agent reachable from the existing Agents list, using a name and an opaque generated resource id. The new document is the exact new_agent_document seed; no Kernel/model/credential/input contract is invented. No auto-save. Existing detail panels configure it, and ordinary Save persists it.

A new draft opens a new sitting (open_id), advances document_revision/version, is READY and dirty, edit_token null, and diagnostics explicitly unchecked. First Save omits expected_edit_token. Successful Save adopts the real token; subsequent saves use CAS. Edits while saving survive, with the successful token advancing. Old load/save replies cannot replace a newer sitting even for the same resource id. Identifier collision is the real edit_conflict, never a silent overwrite or automatic retry. Existing explicit conflict choices remain authoritative.

The hook gains a create command returning the pure factory result; invalid arguments do not replace the current session. The save entry itself uses can_save, so multiple synchronous invocations cannot issue competing first writes. The page accepts stable new-draft arguments and creates without loading a nonexistent id. RecipesPage keeps this distinct from an existing resource selection and clears it when switching back to legacy. The existing resource list offers creation only with a reachable listing and a save bridge, and re-reads successful save announcements. The empty reachable library still offers creation. No native Toolkit/Workflow/Code palette or graph callbacks in this slice.
