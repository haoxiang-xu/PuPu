# v0.1.11 Windows qualification repair

Date: 2026-09-14

## Incident scope

Qualification run `34918980959` verified the sealed candidate, macOS arm64/x64,
and Linux x64, but failed both Windows paths. The restart-update fixture passed
`UNCHAIN_SOURCE_PATH` while the package wrapper consumes
`UNCHAIN_ARTIFACT_SOURCE_PATH`; the resulting fallback directory did not exist
and surfaced as `spawnSync git ENOENT`. The fresh-install path separately lost
the NSIS process exit identity and reported only `unknown failure`.

Qualification run `34923227917` proved that the workflow was still executing
from the immutable `v0.1.11` tag rather than the later `dev` repair. Its complete
log also exposed two downstream fixture-build contract gaps that the old
PowerShell behavior had hidden: no explicit N-1 build version and loss of the
top-level Electron `main` entry when projecting `package.json` into a standalone
electron-builder configuration.

## BC-QUAL-001 — workflow to immutable Unchain artifact builder

- Producer: `_shared-release-windows-restart-update.yml`; consumer:
  `run-with-unchain-artifact.mjs`; boundary: GitHub Actions environment into the
  Windows Node child process.
- Producer shape and canonical representation: absolute checked-out source path
  in `UNCHAIN_ARTIFACT_SOURCE_PATH` plus the exact 40-character revision in
  `UNCHAIN_ARTIFACT_SOURCE_REF`.
- Consumer shape: the same two exact environment keys. Admission is `CLOSED`;
  aliases and mutable refs are rejected rather than projected.
- Failure semantics: a missing directory, wrong revision, or non-zero native
  command stops the fixture build immediately. There is no degraded fixture.
- Identity: the values bind the N-1 published manifest revision to the checked
  out `fixture-unchain` source and the one wheel built for that fixture.
- AC-QUAL-001: the workflow contract contains both canonical keys and the exact
  revision producer.
- AC-QUAL-002: the old `UNCHAIN_SOURCE_PATH` alias is absent from the fixture
  build environment.
- AC-QUAL-003: PowerShell stops on the first failed native build command.
- AC-QUAL-007: every N-1 build command receives the exact `from_version` through
  `PUPU_BUILD_VERSION`.

## BC-QUAL-002 — NSIS process to installed qualification

- Producer: the signed NSIS installer process; consumer:
  `installed-package-qualification.mjs`; boundary: Windows child-process result.
- Producer shape: `status`, `signal`, `error.code`, stdout, and stderr from
  `spawnSync`; canonical representation is a bounded per-attempt diagnostic.
- Consumer shape: success only for status `0` with no spawn error. Admission is
  `CLOSED`; missing output never becomes success and all failures retain process
  identity fields.
- Projection: stdout/stderr become bounded diagnostic text. Unknown process
  fields are ignored; exhausted retries fail closed.
- Identity: installer path and install root remain fixed for every attempt; no
  candidate bytes or manifest identity may change between retries.
- AC-QUAL-004: one transient failure followed by success records one retry and
  returns successfully.
- AC-QUAL-005: exhausted attempts report attempt count, status, signal, and
  error code instead of `unknown failure`.
- AC-QUAL-006: partial output is removed before retry and a cleanup failure is
  terminal.

## BC-QUAL-003 — package metadata to standalone fixture build config

- Producer: immutable N-1 `package.json`; consumer: electron-builder invoked
  with the generated standalone fixture config.
- Producer shape: a non-empty, trimmed top-level `main` entry plus optional
  object-valued `build.extraMetadata`.
- Consumer shape: `extraMetadata.main` in the generated config, preserving the
  original application entry while the updater provider alone changes to the
  loopback qualification feed.
- Failure semantics: missing or malformed entry metadata is rejected before any
  package build; there is no electron-builder preset fallback.
- AC-QUAL-008: the generated fixture config binds `extraMetadata.main` exactly
  to the immutable source package entry.
- AC-QUAL-009: missing or malformed source entry metadata fails closed.

## SEQ-QUAL-001 — bounded Windows installer retry

- Identity key: candidate manifest digest + Windows installer path + install
  root. Initial state is `not_started`.
- Sequence: attempt install → observe exact child result → on failure remove the
  partial install root → wait two seconds → retry, at most three attempts.
- Observable results: success advances to strict installed-resource inspection;
  exhaustion throws the collected diagnostics. Resume/restart/rollback are N/A
  because every hosted job starts from a new temporary root and no report is
  written before full success.
- Persistence boundary: only the final qualification JSON artifact persists;
  failed attempts remain job logs. Related contracts: BC-QUAL-002 and
  AC-QUAL-004..006.

## Release evidence

### Follow-up: run 34934079566, missing unsigned fixture updater config

- Observed failure: Windows job 104268520969 completed the N-1 unpacked build,
  then the strict validator failed with ENOENT for `resources/app-update.yml`.
- Root cause: electron-builder 26.8.1's actual `PublishManager` afterPack handler
  skips Windows `dir` targets. Supplying a generic publish config does not cause
  that target to emit updater YAML. This is not an install/auth/network failure.
- Repair scope: materialize the sole allowed fixture updater configuration before
  signing; keep the strict validator unchanged. Revalidate after both prepackaged
  installer passes. No production feed, candidate bytes, version, or gate is relaxed.
- Dependency path: `PlatformPackager.doPack` returns immediately for prepackaged
  inputs. The two existing Azure-signing installer passes therefore preserve the
  prepared file; they do not need a new build-config input or an extra NSIS build.

#### BC-QUAL-004 — unsigned fixture updater YAML to signed/installed consumer

- Producer: candidate-owned `prepare-qualification-fixture-app-update.mjs`, only
  on the runner-local rebuilt N-1 unpacked payload. Consumer: existing strict
  updater validator before signing, after packaging, and on installed resources
  in `run-restart-update-qualification.mjs`.
- Canonical wire shape: YAML object with exactly `provider`, `url`, and
  `updaterCacheDirName`. Values are `generic`, exact runner loopback URL, and
  `pupu-updater`. Admission is CLOSED; no extra keys or remote feed permitted.
- Projection: only the already-authorized fixture updater feed difference; no
  application/sidecar edits. Publisher identity is checked by the existing signed
  fixture evidence and installed qualification, not invented in the YAML.
- Identity: immutable N-1 tag/source/version remains bound by existing fixture
  evidence; the N candidate and its once-built wheel remain immutable. The file
  is finalized before Azure signing, installer creation, and receipt sealing.
- Failure semantics: absent file is created exclusively; existing matching bytes
  are preserved; unknown fields, foreign providers/cache names, URL drift, or
  missing resources directory fail closed. No overwrite-based repair of bad data.
- AC-QUAL-010: execute installed electron-builder's real afterPack producer for
  Windows dir; prove ENOENT before preparation, then strict admission succeeds.
- AC-QUAL-011: execute its NSIS YAML producer and independently compare its parsed
  output and computed cache identity to the prepared config through the validator.
- AC-QUAL-012: execute real prepackaged doPack twice; updater bytes stay identical.
  A control invocation of the actual writer with production config must change
  those bytes and be rejected, proving the test detects feed drift.
- AC-QUAL-013: unknown fields, wrong cache/provider/URL, invalid URL, and missing
  payload are rejected without overwriting existing data or creating directories.
- AC-QUAL-014: workflow ordering is build → prepare/validate → isolate → sign and
  package → validate-only → seal → install/upgrade; native failures remain fatal.

#### SEQ-QUAL-002 — preparation and repeated prepackaged installer passes

- Identity key: runner fixture payload path + exact loopback feed + N-1 identity.
- Initial state: unpacked payload exists, updater YAML absent. Prepare and validate
  it, move the payload, prime elevation helper, sign payload, package/sign installer,
  validate payload again, seal installer evidence, then install and check its YAML.
- Retry: valid existing config is an idempotent read with byte preservation;
  mismatched output fails. Two prepackaged passes preserve the file. No recovery
  edits after signing; a failed job is restarted with a new runner-local fixture.
- Persistence: payload and installer during the job; existing evidence artifacts
  at completion. No durable user-state mutation; chat/interaction/replay paths are
  N/A for this build-only repair. Actual Windows installed upgrade/restart is
  NOT_RUN locally and must pass on the exact candidate/wheel pair in hosted CI.
- Evidence: AC-QUAL-010..014 are local dependency/CLI/workflow tests, not a full
  Windows signing or NSIS execution. Active rollout remains INCOMPLETE pending CI.
- Local verification: all release-qa tests completed with 252 passed, 1 skipped,
  0 failed. The installed app-builder-lib version used by dependency regressions
  is 26.8.1, matching the immutable `v0.1.10` package lock and failed runner log.
  `git diff --check` also passed.
