# Memory V2「四态判定」的三层划分（0000-0008 鉴定，2026-08-08）

**结论**：`0000-0003#S-0014` D7 那个「多方需要、无 owner」的构件，在 `0000-0008` 里 **被具体化未被解开**。其定义性属性（无 owner）分毫未变。

**核心判据 —— 三层，不是一层**（这是本次最值钱的一条，处方错层的根因）：

| 层 | 内容 | 今天在哪 | 该不该单点 |
|---|---|---|---|
| L1 提取 | `error → code token` | 已单点（`context_v2_bridge.js:57,77-82`），**缺的是强制而非模块** | 该 |
| L2 分类 | `code → 传输/启用类别` | **无人** | 该 |
| L3 呈现语义 | `(类别 × 调用语境) → 用户可见状态词` | 各消费者各持 | **不该** |

- 「统一四态判定」按字面落地会连 L3 一起收 → **我判不成立**。
- `code-owner-chat-bubble` 的 B2 口径 `(error)→{code,kind,parsed}` = L1+L2 止于 L2；`code-owner-chat-core` 的语境分层反对 = 反对收 L3。**两者正交，都成立，都必须进验收标准。**
- **「四份/五份拷贝」这个计数本身是错的** —— 它把 L1/L2 的真重复与 L3 的假重复合并了。错误的度量直接产出错误的处方。

**Why**: 数错了 → 处方「收成一份」→ 落地同时收对（L1/L2）和收错（L3）→ 两个 owner 已声明届时 OBJECTION 并拒绝消费 → 落点定了没人接。

**How to apply**: 任何再提「统一状态判定/统一错误映射」的议案，先问它收的是哪一层。收 L3 的一律不成立。

## 落位鉴定（可复用）

- **判定模块落 `src/SERVICEs/`（与 `boot_readiness.js` 同级），不落 `src/SERVICEs/bridges/`。** `bridges/` 的定义性属性是「不校验、不持状态」，把持规则的模块放进去会削弱使那条契约可执行的东西本身。
- **`memory-inspect/**` 不得成为共享判定的导出点**（前案不成立项 ① 在 0000-0008 重申，新触发面：tree view 进驻后它成了 `src/COMPONENTs/**` 下第一个 V2 浏览面，引力增大）。
- **落位跟随「谁的形状不对就交付不了」** —— 与我前案给接缝 owner 的原则同一条。
- **跨仓归一落 sidecar，不落 renderer/main**：`kind` 词汇权威是 `unchain:MemoryEntryKind`（跨仓 StrEnum），归一必须发生在能 import 它的最近一层；renderer 归一 = 手抄跨仓 enum = boot 先例注释明文反对的那件事。
- **今天没有两套活形状**：`pupu_legacy` entry 形状在 Electron 下结构性不可达（`memory_v2_rollout.js:150` 取值域二元）。为死形状建归一层会破坏三个活消费面 → speculative generality。措辞应是「承认唯一活形状」而非「建归一层」。

## 对我自己前案主张的经验校准（重要）

前案 `#S-0014` 我说：**「传唤机制解不了它，只有指派能解」**。

**0000-0008 证明这句话对了一半。** 传唤确实不产生 owner，但它能把「指派」从开放式判断降为 **二选一并把两边的价开出来**：本案产出了候选 owner 自荐+开价（shared-arteries P1/P2/P3）、替代 owner 被指名（electron，附代价对比表）、口径被两个消费方分别约束（B2、语境分层）、迁移成本逐站点计价（6 站点×≤5 行）。**这是一份完整的指派材料包，前案没有。**

**推论**：材料齐了之后继续拖，成本从「不指派」变成「浪费一次已付过的取证」。

## 可证伪度量（首次出现，应保留）

`code-owner-chat-core` 提出：**「同一个权威码在几份拷贝里被正确处理」，今天 `context_v2_store_disabled` 是 0/5**（该码在整个 `src/` 零命中，三方独立复核）。

**Why**: D7 此前一直是定性论证，无法证伪也无法验收。给结构缺口配可测量指标，是把它从辩论移进工程的唯一办法。

**How to apply**: 下次遇到「无主构件」类鉴定，优先找一个这样的数，而不是继续列举症状。

## 本案单向门（不重复辩论）

1. `getMisoStatusPayload().memoryV2` 升为产品状态契约 = 单向门（15 字段诊断面，含 4 个 sha256，**放行前必须先定投影**；契约测试是必要不充分）
2. 共享判定口径含 L3 = 单向门（三轴词汇碰撞从缺陷变强制）
3. 挂载接口追加第三个位置参数（而非改对象参数）= 单向门；**今天破坏面为零是会过期的窗口**
4. `ownerChatId` 改成跟随活动会话 = 单向门（右键 ≠ 活动会话，错主在链路上结构性不可检测，三道防线全部放行且全部没做错）
5. 给 `contextV2Bridge.getStatus()` 加字段 = 单向门（三方同向反对 + 推翻 expert-security 不传唤判定）

## 取证条件的一条方法论（不只本案适用）

**当唯一可跑的路径与产品实际路径不相交时，每个人的取证会自动变成「在可跑路径上取真结果，再把结论说到问题所需的宽度」。需要的宽度由问题定义，可跑的宽度由环境定义 —— 两者不相交时没有任何个人纪律能弥合。**

0000-0008 里五份 `evidence-examiner` 审查全部判「引用范围宽于证明范围」，是这个结构的必然后果，不是五次疏忽。**唯一处方是把那条路径跑起来。**
