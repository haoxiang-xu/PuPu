# 取证的形状与边界同构 —— 接缝盲区

**规则**：接手任何跨 owner 的鉴定时，**第一件事是做那个减法**（把两侧各自的声明/键集/枚举/契约拿出来对照一次），**在读任何一方的内部之前**。凡跨侧的类型、语义或来源主张，**证据必须来自被主张的那一侧**；单侧 `grep` 推不出跨侧关系。

**Why**（三个实测代价，全在 2026-08-08 case 0000-0005，每条取一条命令）：

| 一条命令就能得到的事实 | 为什么三十余条发言里无人取 |
|---|---|
| 产端 21 键基字面量 ↔ 收端 59 项表 → **7 个被丢** | **减法不属于任何一方。** 产端 owner 数产端的键，收端 owner 数收端的键 |
| sanitize 不在持久化边界上（边界零过滤） | 跨 `shared-arteries` 与 `electron`，**而后者未被传唤** |
| 领先候选的验收 idiom 已在仓内绿着（`expert-qa` 测出） | **测试套件是跨边界制品**，不属于任何 owner 的取证习惯 |

同一模式在质疑上重演：本案被判 **相矛盾** 的 `E-0037` 与在审的 `E-0071`/`E-0072`，**形状完全相同** —— 在单侧作出的彻底观察上，越过接缝作了一步没有证据的推断。**不是尽职程度问题，是取证单元与缺陷单元不匹配**：charter 按边界写，传唤按边界匹配，**没有任何角色的边界声明包含「两个边界之间」**。

**我自己是这个模式的一个实例，不得省略**：`0000-0002-2026-0807#S-0020` 必要条件 2 把根因写成「产端没有声明形状」—— 一个 **单侧诊断**。使它不完整的恰恰是那个减法，而我上一案没做，理由与其他人一样：它不在我传唤到的任何边界内。

**How to apply**：
1. 命中「跨两个及以上 code-owner 边界」触发条件时，**先取接缝证据再取边界内证据**。边界内的东西各自的 owner 会取得比我好，接缝没人取。
2. **别把「缺一份声明」当成根因的终点** —— 先问「两侧各自有没有声明？如果有，它们对得上吗？」。对不上时，缺的是对账（双侧制品，需指名 owner），不是声明（单侧任务）。
3. 提「加一个字段/计数器/记录」类处方前先自查：**写入方与读取方之间有没有判据**。本仓已三次以同一形状失败（`unknownEvents` / `diagnostics` / `journalReload`），而 **那个形状就是本案的缺陷本身** —— 用缺陷修缺陷。可用的替代是 **构建期断言两个可枚举集合的差**，不是运行期的「未知」计数（无产端声明时「未知」恒为真，恒为真的告警必被静音）。
4. **条件写在没人读的地方 = 没写。** 若要给一份裁定挂失效条件，落点必须是 **有人在已知时点被程序要求读的文档**（另一个 case 的 `FRAMING`、发布认证的固定步骤），不是本案的 `ruling.md`。做不到就诚实地不下调 —— 无失效机制的无条件下调严格坏于不下调。
