PuPu 安装意图（安装包下载）是最强真实增长信号。逐版可验证 delta：

- **v0.1.6**（2026-05-25 发布）：06-09 累计 47 → 06-14 累计 64，5 天 +17（≈3.4/天）；生命周期速率 ≈3.2 dl/天。**历史最高。** 自 06-14 起冻结在 64（用户已迁移到 v0.1.7，老版归零符合一贯模式）。
- **v0.1.7**（2026-06-14 发布）：06-23 累计 21 → 06-26 累计 23，**3 天仅 +2（≈0.67/天）**；12 天生命周期速率 ≈1.9 dl/天。**明显低于 v0.1.6 同龄速率（3.2/天），约为其 60%。** 平台分布反转：linux deb 13 / win 7 / **mac dmg 仅 3**。
- v0.1.5：73；v0.1.4：63。均已归零。

- **v0.1.7（2026-07-05 更新，发布21天）：累计 36（dmg 11 / exe 9 / deb 16）。** 06-26→07-05 的 9 天 +13（≈**1.44/天**),对比前一段(06-23→06-26)的 0.67/天 **速率翻倍、在加速**;生涯速率升到 1.71/天。**平台反转再反转:mac dmg 3→11(9天+8)成为增长引擎**,linux/win 平缓。之前"linux主导mac垫底"的观察本周被推翻——mac 自动更新通道未证实,但 dmg 手动下载确在猛涨。

**判定（2026-06-26 旧）：安装速率出现回归信号。** v0.1.7 dl/天低于前一版,已交 release ops。
**判定（2026-07-05 更新）：回归信号在自我修复。** v0.1.7 起步冷、现速率翻倍追赶,但生涯 1.71/天仍仅为 v0.1.6 当打期(3.2/天)的约一半 → 保留 flag 但降级:根因更像"发布静默/传播不足"而非版本吸量缺陷。已请 release ops 复盘 v0.1.7 发布传播动作。

**v0.1.8（2026-07-13 发布，2026-07-21 巡检=发布第8天，首个表现窗口）：累计 19（deb 11 / exe 5 / arm dmg 3 / intel dmg 0）= 2.375 dl/天。** 关键同龄对比:v0.1.7 第9天(06-23 快照)=21→2.33/天。**v0.1.8 与 v0.1.7 早期速率基本持平、甚至略高 → 回归没有继续恶化,是同一横盘,不是新一轮下跌。** 但仍低于 v0.1.6 黄金期(~3.2/天)约74%。平台再现 v0.1.7 早期形态:**linux deb 主导(58%)、mac dmg 仅3(垫底)、intel dmg 0**。v0.1.8 无 mac zip 资产→mac 只能手动下 dmg,mac 通道弱是结构性的(同 v0.1.7)。**v0.1.8 首窗为单快照,其自身周 delta=baseline saved, 下周对比。**
**老版仍在吸量(反常但真):** v0.1.7 在有后继版本后仍 36(07-05)→56(07-21)=+20/16天(1.25/天),没归零;v0.1.6 +6。近16天全活跃版合计约+45 dl≈2.8/天,比单看 v0.1.8 健康。说明用户经搜索/直达仍在下老版,自动更新未把人迁走(或下载计数含更新检查)。
**判定（2026-07-21）：v0.1.8 冷启动=曝光问题而非产品问题。** 发布日(07-13)90 view 尖峰但仅7独立访客、release 页仅1独立访客→v0.1.8 是"发进真空":零社交零社区放大。这直接印证战略命题「曝光卡在 0.1.9 第一印象就绪」。对 0.1.9 曝光决策的信号见下方 How to apply 与 [[exposure-ceiling-channels]]。
**可能的良性解释（须证实，勿当定论）：** ① mac 自动更新走 .zip 通道、不增计 .dmg → mac 3 可能被低估；但 v0.1.7 资产里似乎无 mac zip，若确无则 mac 用户只能手动下 dmg、3 就是真低。② Windows NSIS 自动更新会增计 .exe，故 win/linux 数更接近真实新装。release ops 应确认 v0.1.7 的 mac 自动更新通道是否存在。

**平台偏好变化：** v0.1.6 三平台均衡（23/22/19）→ v0.1.7 linux 主导、mac 垫底。发布仍须三平台齐发；mac 通道要单独查。

**v0.1.9（2026-08-01 发布，2026-08-07 巡检=发布第6天）：累计 17（deb 11 / exe 6 / arm64 dmg 0 / 无 intel、无 mac zip）= 2.83 dl/天。** 同龄对比:v0.1.7 第9天=2.33、v0.1.8 第8天=2.375、v0.1.6 黄金期≈3.2。**v0.1.9 冷启动速率是 v0.1.7 悬崖以来最好的一版,首次向黄金期回升——「0.1.9 第一印象就绪」的战略押注在安装侧兑现了。** 但两处硬伤:① **mac 彻底归零**(arm64 dmg=0,且仍无 mac zip→mac 用户零安装记录,结构性 mac 弱进一步恶化);② linux deb 65% / win 35% / mac 0%。
**窗口聚合速率下滑(诚实标注):** 07-21→08-07(17天)全版新增下载:v0.1.9 +17、v0.1.8 +16、v0.1.7 +0、v0.1.6 +0 = 约 +33 ≈ **1.94/天**,低于上一窗(07-05→07-21)的 ~2.8/天。但下滑主因是 **v0.1.7/v0.1.6 老版尾流冻结**(上一窗 v0.1.7 还在 +20,可能含更新检查噪声),不是新装意愿降——最干净的信号是 v0.1.9 自身冷启动 2.83/天,是升的。别把老版尾流枯竭读成新装下滑。

**leak(b) 确认并延伸(台阶在 v0.1.6→v0.1.7,非 0.1.8):** 冷启动速率链 v0.1.6≈3.2 → v0.1.7≈2.33(悬崖)→ v0.1.8≈2.375(横盘,没继续跌)→ **v0.1.9≈2.83(首次回升)**。0.1.8 从来不是回归点,v0.1.9 是悬崖后第一次向黄金期爬。
**leak(a) 用本次数据确认(自动更新自 v0.1.5 死):** 逐版查 assets——**v0.1.5/6/7/8/9 全部无 latest*.yml 更新清单**(electron-updater 靠 latest.yml/latest-mac.yml/latest-linux.yml 探更,全缺=更新源不存在=自动更新结构性瘫痪);唯一带清单的是 v0.1.2/v0.1.4。搁浅基数=v0.1.5→v0.1.8 下载 77+70+56+35=**238(≈250)** 用户装了就再没有更新通道,每次安装都是一次性。已交 COO/release-ops + dev-electron:修 electron-builder publish 配置让每版产出并上传更新清单。

**Why 这条重要：** CEO 数据优先且最看重「有没有人真在装」。**2026-08-07 转正向:v0.1.9 冷启动是一年内最好,产品就绪已被安装数据证实。** 运营建议随之转为「趁 v0.1.9 新鲜、组织一次放大发布」+「补死掉的自动更新管道」。
**How to apply:** 每次巡船 diff 最近 release 的 download_count 算 dl/天并与上一版同龄对比;并 diff 老版尾流是否冻结(算干净的新装 vs 聚合)。下次重点:v0.1.9 速率能否守住 ~2.8、mac 通道(arm dmg/zip)有没有修、自动更新清单有没有回来。相关：[[clone-spike-2026-06]]、[[silent-downloader-gap]]、[[exposure-ceiling-channels]]。
