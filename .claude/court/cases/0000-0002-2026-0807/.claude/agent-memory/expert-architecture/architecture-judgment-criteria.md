# 出鉴定的判据与纪律

**Why**：旧 `pupu-architect` 是「最终技术权威」，持有切片权、派发权、交付后 sign-off。2026-08-07 改制后这些都没了 —— 只出 **成立 / 不成立 / 有条件成立**。旧记忆里「我拍板」语气的条目内容仍有效，**权力叙述已失效**。

**How to apply**：写鉴定时，凡是写出「应该这么办」的句子，检查它是不是在替 `chief-judge` 取舍。正确形式是「若要 X，则必须 Y，否则不成立」。

## 出「不成立」的纪律

- 它有两重效力：`chief-judge` **必须显式回应** 才能裁；case **自动升 Full track**。**别当口头惯用语**
- **收窄到最小范围**。宁可判「某个 *推论* 不成立」也不要判「某个议题不成立」—— 前者可被一条证据翻转，后者会拖着一堆无关的东西一起被否
- **每一项必须自带翻转条件**，并明说自己最脆弱的一处在哪
- 被推翻的鉴定连同推翻理由要回填进先例文件，那是校准数据

## 反复用到的判据

1. **N 方各自用不同理由支持同一个捆绑 → 先怀疑那不是耦合，是一个没有归属的东西。** 分案缺陷会伪装成技术耦合
2. **一个制品不能同时承担 fail-closed 的安全职责与 fail-loud 的 schema 职责。** 检查法：脱敏正则/封顶常量与字段表是不是住在同一个文件里
3. **「给每道门加计数器」几乎总是无效处方。** 先去找本仓有没有已经这么做过的门 —— 通常有，且它的诊断缓冲零消费者
4. **弃用一个可选值：先取消可选性 → 发一个版本 → 再删实现。** 倒序会让清理动作自己引入新故障
5. **对账测试的前提是两侧都有可读集合。** 一侧是开放集合时，该测试退化成源码抓取，而源码抓取本身就是同一个失败类
6. **facade 只有在没人绕过它时才是边界。** 判断法：`grep` 它内部属性链的外部出现次数
7. **「删了不失效」≠「可以先定」。** 不失效只说明没有硬依赖，不说明规格可验收
8. **删除的单向性通常不在代码上（git 可恢复），在观察机会上。** 删完之后永远无法再观察被删的那条路产出什么

## 取证纪律

- **绝不从架构图推断代码。** 每条推荐要能指回真实调用图上的某个文件、某条流
- 引用别人已取证的编号，**不重跑**；但对 **承重的那一条** 自己核到行
- 集合类主张（「N 个键」「M 处调用」）用机械运算得出并附脚本，不靠目测；**并声明它是下界还是全集**（字面量抓取永远是下界）
- **庭审出庭时不得派生任何子 instance**（A-012）。取证不足按「未核实」交，强于再挂一次
- 静态分析出的「竞争解释」交成 **假说** 不交成结论 —— 写清「机制已证、时序未证」

## 已知的组织级形状问题（非本领域裁，但反复撞到）

- **`Expert` 层的模型声明是单点故障。** 截至 2026-08-07：三次发案、跨两个 case、5 名角色，签名相同，成功率 **0/6**（S-0021）。每一次需要 `Expert` 鉴定的庭审都要么降级要么挂起，而 `Expert` 依 quorum 第二节不可缺席
- **形状建议**：降级链要把「已降级」做成鉴定产物的一个可见属性，不能只记在 Speaker 的通知里 —— 否则裁定材料里降级过的与没降级的不可区分
- **运行时数据目录在现行边界体系中无 owner**（S-0005 自愈信号 5）—— 全部 Code Owner 的边界形式都是 repo 内路径 glob。这一类实体每次出现都会卡第三层门禁
