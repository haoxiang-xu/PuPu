**结论：清理循环没有"最终放弃"这个状态。孤儿只能来自 outbox 记录本身丢失，不能来自重试耗尽。**

**（一）没有终态失败**（`deletion_outbox.js:8-12`）：

```js
const OUTBOX_STATUS = Object.freeze({
  PENDING: "pending", RETRY: "retry", COMPLETE: "complete",
});
```

**枚举里没有 FAILED / ABANDONED / DEAD_LETTER。**

**（二）没有重试上限**（`:202-229`）：`persistRetry` 无条件把状态置为 `RETRY`，`retryCount + 1`，退避 `min(250ms * 2^min(n,16), 60_000)`。**`retry_count` 从不与任何阈值比较**，全文件不存在 `MAX_RETRY` 类常量。四条失败分支（`STATIC_ERROR_CODES` 的 CONTEXT / VAULT_USE_STATE / VAULT_LIST / VAULT_DELETE，`:285-389`）全部走 `persistRetry` 后 `return`，无一条丢弃行。

**（三）唯一的删行语句只删已完成的行**（`pruneReceipts`，`:231-239`）：`DELETE FROM chat_deletion_outbox WHERE status = 'complete' AND ...`。**未完成的行不可能被 prune 掉。**

**（四）取行条件不会跳过老行**（`nextDue`，`:265-273`）：`WHERE status != 'complete' AND next_attempt_at <= now ORDER BY next_attempt_at ASC` —— 最老的到期行永远排在最前。不存在饥饿。

**（五）因此孤儿凭据的必要条件是**：`chats.db` 里的 `chat_deletion_outbox` 行消失，而 `settings.db` 里的 `vault_secrets` 行还在。两者是**不同的数据库文件**（vault 在 `userData/settings.db`，见 `memory_vault/service.js:29-32, 47`；outbox 在 chats.db）。可能的成因：用户手工删除或损坏 `chats.db`、只重置 chat 存储、迁移丢表、备份还原时两库版本不一致。**这些都不是"清理失败"，而是"记录被移除"。**

**（六）一个正向事实（对处置方案有直接价值）**：只要 outbox 行还在，`row.owner_chat_id` **就是那个孤儿 scopeId**。也就是说，未完成的 outbox 行是主进程内 **已有的、无需新增任何能力的** 孤儿 scope 发现机制。真正不可发现的，只有连 outbox 行都没了的那一类。
