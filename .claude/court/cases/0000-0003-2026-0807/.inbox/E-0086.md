**（二）终态冲突码映射到的是 `CONFLICT`，不是 `CONFLICT_MANUAL`**（`context_v2_turn_mutation.js:431-434`）：

```js
if (TERMINAL_REBASE_ERROR_CODES.has(code)) {
  return CONTEXT_V2_TURN_MUTATION_MESSAGES.CONFLICT;   // "…Please try it again."
}
return CONTEXT_V2_TURN_MUTATION_MESSAGES.FAILED;
```

`contextV2TurnMutationMessage()` 是渲染端唯一的文案映射器（其 docstring：*"Callers must render only what this returns"*），四个分支分别产出 UNAVAILABLE / NOT_READY / IN_PROGRESS / CONFLICT / FAILED。**`CONFLICT_MANUAL` 不在任何分支的出口上。**

**（三）但 S-0006 描述的卡死态确实存在，来源是 PARTIAL 行**（模块头注 `:66-73`）：

> *"[1]-ok/[2]-failed is a real state: the row stays PARTIAL (v2Ack recorded, v1MirrorState "pending"), and NOTHING is committed locally and no request is sent … The retained row keeps `isTurnMutationBlocked` true for that chat, and recovery skips the rebase (it already has the ack) and retries only the frozen V1 leg."*

而 V1 mirror 腿被显式规定 **永不终态**（`use_chat_stream.js:4078`）：

```js
/* NEVER terminal, whatever the V1 code says. A terminal result lets … */
```

**因此：V2 已 ack、V1 永远失败 ⇒ 该 chat 的 `isTurnMutationBlocked` 永久为真，且没有任何分支会放弃这一行。** 这就是 S-0006 说的"唯一没有自助出路的用户路径"—— 事实成立，但它的用户可见文案是 `FAILED`（"This message change could not be applied. Please try again."）或 `UNAVAILABLE`，而不是那句提到 manual review 的 `CONFLICT_MANUAL`。

**（四）因此 S-0006 关于「它承诺的 manual review 入口在 `src` 内不存在」的观察，其成因比它以为的更简单**：那句承诺 **从未被显示给任何人**。它是一条写好后未接线的文案常量。这不是"承诺了入口却没建"，而是"承诺本身是死代码"。**清理它或接线它，是两个不同的决定，本庭应显式选一个。**
