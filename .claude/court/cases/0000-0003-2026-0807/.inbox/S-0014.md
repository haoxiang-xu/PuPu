### 一 · Q1 —— 四态该不该有单一状态源？**成立**

#### 1.1 先给一条本案还没有的测量

我做了三次全仓普查（E-0091），结果比十一份发言里任何一条都更能说明问题：

| 信号 | 富度 | `src/**` 非测试调用点 | 分布 |
|---|---|---|---|
| `getSessionHead` | 十余个判别字段 | **1** | `use_chat_stream.js:3916`，且在 **turn mutation 的写前置**里 |
| `getContextV2Status` / `getStatus` | 多字段状态 | **0** | 能力在 main 里实现并导出（`service.js:1945, 5871`），renderer 一次没用过 |
| `isAvailable()` | **恒真** | **6** | chat-bubble 4 + chat-core 2，横跨 2 个 owner |

`S-0006` 自陈那条 head 读「不是一个公共的记忆就绪度读」。我把它收紧一档：**它在调用图上连读路径都不是。** 想拿到全应用唯一能区分四态的信号，唯一方式是发起一次 turn mutation。Inspector、气泡、vault 面、devtools fixture —— 没有一个够得到它。

#### 1.2 不建单一源的代价，不是预测，是已经全额发生了

**五条代价，五个不同 owner，同一个成因。**

#### 1.3 落位与归属：不需要发明，本仓已经建过一次

这是我这次最重要的取证（**E-0090**）。`src/SERVICEs/boot_readiness.js` 的文件头逐字写着：

> Owns the one subscription to window.bootReadinessAPI and translates what main reports into two things: 1. the `backend` gate — the hard "may the user in?" answer, 2. a small presentational state … the BootOverlay renders while the gate is closed.
>
> It is split from boot_progress.js **on purpose**: boot_progress stays a dumb progress/gate primitive … while everything that knows about sidecars, MCP and retry lives here.

四条结构属性，逐条对上本案：

| boot 侧的属性 | 本案对应的缺口 |
|---|---|
| **唯一订阅点**，消费方不各自探测 | 6 个 `isAvailable()` 各自探测（E-0091） |
| **判定与呈现分离**（模块产出状态，`BootOverlay` 只渲染） | `memory_inspect_modal.js` 自己请求、自己判 `points.length===0`、自己渲染（E-0002） |

| **模块级 store + `subscribe()`**，不是 context provider | 与工程铁律「不新建 context provider」相容 —— 建同形模块**无需新 provider** |

再加一条方向性的：boot 是 **push**（`onBootReadinessChange`），且后端起来后又死掉时**显式重新关闸**（`applyReadiness` 注释逐字 "Re-close on a backend that died after coming up"）。**与 E-0003 的 Inspector 静默轮询正好相反** —— 同一个「状态会变坏」的场景，本仓两处结论相反，而 boot 那处是对的。

main 侧配套（E-0090 §三）：`FAILURE_CODES` 是 `Object.freeze` 枚举，**两道方向相反的守卫**：

- `boot_readiness_service.test.cjs:256-277`，用例名逐字 `"every emittable failure code is declared in FAILURE_CODES"` —— **main 发得出的码 ⊆ 枚举**
- `boot_locale_parity.test.js:42-47`，`require` main 模块取枚举 —— **枚举 ⊆ 11 locale 的键**

其注释逐字给了为什么必须 import：

> Read the emittable codes STRAIGHT FROM MAIN rather than transcribing them: a hand-copied list silently stops covering a code the day someone adds one.

**归属结论**：
- **权威状态码枚举 → `code-owner-electron`**（`electron/main/services/**`，且必须配枚举完整性测试）
- **renderer 侧唯一就绪度读 → `code-owner-shared-arteries`**（`src/SERVICEs/**`，与 `boot_readiness.js` 同级同形）
- **消费方（Inspector / 气泡 / vault 面 / devtools）一律退化为渲染方，不持有判定**

**这不是新契约面，是既有的、已验证的两 owner 协作形状的第二个实例。** 可逆：新增一个 SERVICEs 模块，消费方逐个迁移，不迁的照旧工作。

### 二 · Q2 / Q5 —— 落位、接缝形态、接缝归属

#### 2.1 分流放 modal 内部：**成立**，但正确理由不是已归档的那两条

我自查确认了接缝的逐字现状（与 S-0008 一致）：

- `side_menu_context_menu_items.js:199-207` character 分支传 `buildCharacterMemorySessionId(...)` 的**派生串**
- 同文件 `:218-224` 普通分支传 **`node.chatId`**
- 两者进 **同一个位置参数**：`onInspectMemory(x, chatTitle)`
- `side_menu.js:296-299` 无差别存成 `{open, sessionId, chatTitle}`
- `:771-778` 传给 modal，props 只有 `open / sessionId / chatTitle / onClose`
- **modal props 里没有 chatId、没有 chatKind、没有 characterId** —— 确认

`S-0006` 给的两条硬理由（入口是纯同步构建器 / 点击后开 modal 前无 loading 面）我确认属实，但它们是 **实现约束**，明天换个实现就可能被解除。裁定不该建在会消失的理由上。

**结构理由（不依赖任何当前实现）**：分流判据的词汇表 **会增长** —— 今天至少 8 个码且随 `store_owner` 变形（E-0008），后端 `route_memory_v2.py` 有 35 个 `context_v2_*`（S-0007），main 侧另有 11 个 reason（E-0031）。**把一个会长大的判定放在一个必须保持 O(1) 同步的位置，是结构错配。** 菜单构建器永远不该承载增长中的词汇表，无论它将来同步还是异步。

顺带确认 `expert-ux`（S-0012 §7 末）那条追加判定并给出架构理由：**admission 结果不得改变菜单条目集合与顺序**。菜单项集合是一条 **用户可预测性契约**；把它绑到一个异步、会失败、且是 boot 时快照的信号上（E-0031），等于让一个已知不可靠的信号驱动一个必须可靠的东西。这条与 ux 的肌肉记忆理由**独立成立**，两条理由可以互为备份。

#### 2.2 「位置参数换对象、chatId 与 sessionId 拆两字段」：**成立，且是必要条件不是优化**

三条理由，第三条是决定性的：

1. **今天这个位置参数承载两个不同类型** —— 一个 opaque 的派生 wire 串，一个 chat 主键。JS 里位置参数的类型错配是**静默的**（S-0006 约束 4 已指出）。
2. **下游破坏面为零**（E-0016，我自查确认：单挂载点、单消费者、两个写点）。所以这是**零成本的**必要条件，没有权衡可做。
3. **决定性的一条**：`buildCharacterMemorySessionId` 是 **有损多对一**（`toLowerCase` + 非 `[a-z0-9]` 连续段替换 + 空值 fallback，E-0033），且 `chatId` **从未被编码进产出串**。因此「从 sessionId 嗅探出 chatId」**在原理上不可靠**，不是「今天没做」。

**推论（请本庭记入）**：若分流建立在字符串前缀嗅探上，那是 **把一个契约问题伪装成解析问题**。它会通过所有测试，然后在第一个 chatId 恰好长得像派生串的用户那里静默走错分支。这类缺陷没有失败信号。

#### 2.3 接缝归属：**这条接缝今天无 owner，该现状不成立**

这是本案第二条结构信号，也是我认为最需要 `chief-judge` 亲自处置的一条。

接缝跨三个 owner，而 **三方的主张都正确**：

| 角色 | 主张 | 我的核实 |
|---|---|---|
| `code-owner-chat-core` | 承诺扩展、破坏面零，但自陈**入口放哪一层是越界，主动交出** | 正确 —— 落位判断确实不该由供给方做 |
| `code-owner-shared-arteries` | 只给 `buildCharacterMemorySessionId` 的**可改性结论**，不主张调用侧处置 | 正确 —— 函数本体与调用形态是两件事 |
| `code-owner-settings` | 承接 **modal 内部**，并要求裁定措辞消歧（读法 A / 读法 B） | 正确 —— 且它对读法 B 会毁掉 per-chat Inspector 的判断我确认成立（settings 侧挂载点无 chat 上下文） |

**没有人错。合起来没有人拥有这条接缝。** 传唤机制不产生 owner —— 它只把已有 owner 叫到场。

**我的鉴定（不是指派，指派权属 `chief-judge`）**：接缝的 owner 应当是 **consumer 端**，即 `code-owner-settings`。理由：它是唯一一个「参数形状不对就交付不了」的一方，因此是唯一有持续动力维护该形状的一方。供给端（`code-owner-chat-core`）的义务是**按 consumer 声明的形状供给**——它已承诺，且破坏面为零。

**这不是我发明的原则，是本仓 boot 先例里的同一条**：`src/SERVICEs/boot_readiness.js` 声明它要什么形状，main 侧供给并用测试守住（E-0090）。消费者定形状，供给者守契约。

### 三 · Q4-B —— `settings > local_storage` 落位与「能力不完整的底座」

#### 3.1 落点：**成立**，但正确理由是生命周期不是心智模型

`S-0006` 拒接的四条理由里，第 3 条（心智模型上属 settings）是最弱的一条 —— 心智模型可以被设计改变。我给一条结构理由：

**captured secret 的生命周期 long 于 chat 的生命周期。** `S-0010` C-1 已证：chat 删除后 chat 域凭据**仍然存在**（且 scopeId 从此不可构造，成为孤儿，E-0055）。**一个生命周期长于宿主的对象，其管理面不能挂在宿主上** —— 否则宿主消失时管理入口一并消失，而对象还在。这正是孤儿凭据「不可见不可删」的结构成因之一。

这条理由与 `S-0006` 的四条同向，但它不依赖任何关于用户心智的假设。

#### 3.2 「是不是在为一个能力不完整的底座建界面」：**是，但我不判『不该建』，我判『必须先建能力』**

我自查确认了 `expert-security` E-0081 的核心事实：`grantId` 只在 `service.js:2190` 铸造、`:2217-2224` 消费；`listDescriptors` 只回 `grantCount`（`:2115`）；**全仓无任何路径返回 grantId 列表** → `revoke` 字面不可调用。我确认 `expert-security` 的判定，不复判其安全定级。

**架构上的要害是可逆性，不是完备性**：

一个界面一旦发布，就成为 **用户对系统能力的契约声明**。

- 发一个「能看、不能撤」的清单，之后再补 revoke —— 用户侧是 **加法**，**可逆**。
- 发一个把 `grantCount` 显示成「3 个授权」却撤不掉任何一个的界面 —— 这是 **在用户面上做了一次不实陈述**；收回它要同时改文案与改行为，是 **双向成本**。

所以 `expert-ux` C-UX-4(c)（`grantCount` 在档 A 落地前不显示）**我判成立，并把它从「条件」升为「不成立项」**（不成立事项 ⑤，与 C-UX-4(c) 同向，非独立发现，可与之合并处置）。

### 四 · Q7 —— 形态改判：**成立**（同意），但因果关系要说得更精确

#### 4.1 我自查确认的两条事实

- `src/COMPONENTs/chat-bubble/artifact-summary/` 8 个非测试文件，`ref` / `pupu://` **零命中**（确认 E-0041）
- 全 `src/` 非测试 `pupu://` **零命中**（确认 E-0040 / E-0048）

#### 4.2 同意改判，但「因变量在我这一面」的表述会被误读

`code-owner-chat-bubble`（S-0009）原话是「因变量在我这一侧，不在契约那一侧」。**结论我同意，表述我要更正**，因为它在架构上是反的：

- 严格地说，**契约是自变量，呈现是因变量** —— 呈现能做什么，由契约喂什么决定。
- 但本案问的因变量是 **「用户看到什么」**。在这个函数下，**两个候选自变量取值（新增 `listArtifacts` / 走 refs）映到同一个因变量值：零**。

所以 Q7 **不是「选错了自变量」，而是在因变量对该自变量不敏感的区间上做选择** —— 区间内任何取值都不改变输出。

**这就是为什么「先裁契约」会得到一个不产生任何用户可见变化的裁定：不是裁错了，是裁了一个此刻不影响结果的自由度。**（不成立事项 ④）

**正确的提问顺序**：先定 artifact 在气泡上 **是不是一个用户可见对象**。
- 裁「否」→ Q7 整题消失，`listArtifacts` 与 refs 都不必议。
- 裁「是」→ 才轮到契约，而那时判据是清楚的：`S-0010` D-3（能复用 `READ_CONTENT` 的 ref 文法就复用，净新增只有「列举」一条）**我判成立**，它把攻击面增量压到最小。

落点同意 `expert-ux`：唯一落点是 `ArtifactSummary`。架构侧理由：`pupu://` 不得 linkify 是一条硬约束（S-0009 约束 4，我自查确认全仓无协议注册），故 ref 必须以 **受控元素** 呈现；受控元素只能长在拥有该 bucket 的组件里。

#### 4.3 一条本案至今无人指出的架构风险（charter 主动指出义务）

`S-0007` Q7-2 已证两件事：ref 是 **revision-pinned**，同一 ref 永远指向同一份 bytes；但 **store owner 从 `pupu_legacy`/`off` 切到 `unchain` 时，两套 ref 语法不同源**。

把这两条与 `S-0010` 的实测（E-0056 / E-0057：现网默认 `store_owner === "off"`）合起来读：

> **任何被持久化进已落库消息体的 ref，在 store owner 切换那天会整批失效。**

而切换是 **计划中的**，不是假想。这条的分量在于：ref 一旦进了已落库的消息，它就 **从一个瞬时寻址符变成了一份历史数据**，而历史数据不随 store owner 迁移。

**所以「把 ref 写进气泡的持久渲染数据」是一个单向门的前置条件，必须在裁「是」之前回答**（C-ARCH-5，单向门清单第 5 项）。这一条本案此前无人提出。

我的架构鉴定是：**「给用户一个出口」结构上成立，且是必需的。** 理由不是体验，是终态可达性 —— `S-0006`（E-0015）已证该分支 **既不 `removeTurnMutation` 也不 `releaseTurnMutation`**，而其指纹相同的兄弟分支两个都调了。**即：它是全系统里唯一一个没有出路的终态。**

一个没有出路的终态在架构上不可接受，因为它把一个 **本该瞬时的失败** 变成了 **持久且不可清除的状态**，而该状态锁住整个会话（禁发送 + 禁全部消息按钮 + 禁换模型，E-0014）。**出路是必需的；出路的形态（丢弃 / 重试 / 人工审阅）可选。** 我同意 `S-0006` 的投产比判断：manual review surface 是给一个 16:2 分辨率的失败态配全新界面，不划算；最小形态取「丢弃」。

**但丢弃动作本身在数据侧是单向门** —— 已丢弃的用户改动不可恢复。所以它需要一次确认，且确认文案必须说清丢弃的是什么。这与安全无关，是数据一致性取舍，正如 `expert-security` 所说，属我与 `code-owner-chat-core`。

### 六 · Q6 与 Q7（优先级、约束扩写）

#### 6.1 Q6 优先级倒序：**有条件成立**，`expert-ux` 的条件 **必要但不充分**

倒序（先做 V1 projection 四态）**不会造成返工，当且仅当先建 C-ARCH-1 的单一状态源**。

`expert-ux` C-UX-3（词汇文案一次定义、两处共用）方向正确，但 **不充分**，理由是本案自带的两条反例：

- **E-0039**：`use_chat_stream.js:414-427` 已有一张 code→键映射表，**它引用的 6 个键在 11 个 locale 里存在数为 0，包括 `en.json`** —— 活到今天没人发现。
- **E-0037 / S-0008**：`CONFLICT_MANUAL` 常量与实际渲染的内联串 **逐字不同**（"change" vs "operation"），其中一份是死代码。**这正是「同一个语义两处各写一遍」的直接产物。**

而 `boot.*` 那 11 个键 **零缺口**（E-0036 实测），机制不是「大家说好共用」，是 **`boot_locale_parity.test.js:42-47` 从 main `import { FAILURE_CODES }` 而非手抄**，加上 main 侧 `boot_readiness_service.test.cjs:256-277` 断言每个可发出的码都在枚举里（E-0090）。

**结论：共用必须由 import 强制，不由约定维持。** 充分条件即 C-ARCH-2 的三条 (a)(b)(c)。缺任一条，倒序都会返工 —— 不是因为 V1 白做，是因为 **V2 上线那天会长出第二套 switch**，而没有任何测试会发现它（E-0039 就是这个机制的实证）。

我同意 `code-owner-devtools` C-3（devtools 的四态 fixture 排在 Q8 之后），并加强一条：**fixture 必须从同一个权威枚举生成**，否则 fixture 自己就是第三套词汇。

#### 6.2 Q7 议案自带约束的扩写：采纳 **成立**，但「扩写已充分」**不成立**

`code-owner-runtime` C2（「任何被 Inspector 用来判断四态的读端点，其 200 body 必须带一个显式的状态判别位」）**应采纳**。E-0024 的举证充分：`events` / `spaces` / `candidates` / `reviews` / `promotions` / `jobs` 六个端点已经是同一形状，只约束一个端点等于把同一个 bug 换个入口继续存在。

**但它仍写窄了，两处**（不成立事项 ③）：

**(一) 「被 Inspector 用来判断四态的」—— 判定 surface 不止 Inspector。**

本案已点出至少四处会渲染「没有」：Inspector 的 empty、`ArtifactSummary` 的 `return null`、`RefReader` 的 `canRead=false` 无按钮无解释、以及尚未建的 vault 列表（`expert-ux` 请求 2）。约束应按 **surface 无关** 写：**任何渲染「没有」的位置，其「没有」必须来自一个肯定信号。** 我确认 `expert-ux` R3、`code-owner-settings` C1/C2、`code-owner-runtime` C2 **是同一条约束的三次独立发现**，应合并成一条写进裁定，而不是三处各写一遍——否则它自己就会重演 E-0037。

**(二) 只约束 200 body，不约束 error code 的枚举完整性 —— 这是更贵的那一半。**

判别位解决「这个 200 是哪一种 200」，**不解决「这个 code 前端认不认识」**。反例已在案卷里：`context_v2_readiness_failed` 在 `src/**` 检索 **0 行**（E-0032），于是落进兜底 `FAILED` 并说「请重试」，而按机制该重试 **永远不会成功**（E-0031，boot 时快照，本进程生命周期内不刷新）。**端点带了判别位也救不了这个 —— 前端不认识那个码，结果一样错。**

**我建议的完整扩写（三条，缺一不可）**：

- **(a)** 任何被用来判断四态的读端点，其 200 body 必须带一个显式的状态判别位；
- **(b)** 任何会跨进程边界到达 renderer 的状态码，必须在 **一个单一权威枚举** 里声明，且有一个测试断言 **「每一个可发出的码都在枚举里」**；
- **(c)** renderer 对 **未在枚举中的码**，必须落进一个 **显式的第四类**（「说不清」），且该类在视觉上 **与「为空」不同形**。

**(b) 与 (c) 不是我发明的** —— 它们是 `boot_readiness` 今天已经在跑的两道守卫加一个 `unknown` 兜底（E-0090）。

#### 6.3 Q3 —— 我只就依赖形态出鉴定

内容取舍我不表态（开发面非产品面）。但 `code-owner-devtools` 的 C-1（devtools 面不得引入任何 `SERVICEs/bridges/*`、`window.*API` 或网络调用）与 C-2（devtools 面不得自行实现任何判定）**我判成立，且这两条正是 C-ARCH-1 的推论**：一个 fixture 驱动的离线样机，其价值恰恰在于它消费的是 **与产品面同一个判定函数**，只是喂它假数据。若 devtools 自己写一套判定，那就是第九个自判点，样机验的是它自己而不是产品。
