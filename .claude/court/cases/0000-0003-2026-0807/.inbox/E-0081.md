**（一）`revoke` 只接受 `grantId`，且强校验格式**（`service.js:2212-2226`）：

```js
const { operationId, grantId } = payload;
validateOperationId(operationId);
validateGrantId(grantId);      // 必须匹配 /^pvg1_[0-9a-f]{32}$/
... "DELETE FROM vault_grants WHERE grant_id = ?"
```

**没有 `revokeByHandle`，没有 `revokeAllForScope`。** 撤销的唯一入参是 grantId。

**（二）`grantId` 在整条链上只出现一次，且是"写后即不可见"**：
- `grant()` 的返回体是唯一给出 `grantId` 的地方（`service.js:2196-2204`）。
- `listDescriptors` 的投影里 **没有 grantId** —— 只有 `grant_count`（`service.js:2099-2100, 2115`），一个数字。
- **没有任何 `listGrants` / `getGrants` 方法。** service 的完整导出集（`service.js:2326-2348`）是：`init, deposit, listDescriptors, deleteSecret, grant, revoke, prepareUseIntent, bindPreparedUseIntent, confirmBoundUseIntent, isBoundUseInteraction, executeUseIntent, cancelUseIntent, deleteUseStateForOwnerChat, configureSinkExecutors, startSinkBroker, stopSinkBroker, getSinkBrokerBootstrap, getStatus, close`。逐项核对，无一返回 grantId 列表。

**（三）由（一）（二）得到的死结**：一个管理界面要提供"撤销"，必须先知道有哪些 grantId。今天唯一得到 grantId 的方式是 **自己刚刚调用过 `grant()` 并把返回值记在内存里** —— 而 `grant` 在 `src/**` 有零非测试消费者（E-0034 已核实）。因此：

> **今天不存在任何进程曾持有过任何 grantId。`revoke` 在字面上不可调用。**

要让 revoke 可用，**必须新增一条 main→renderer 的读通道**（返回 `grantId + sinkKind + createdAt`）。C7 写的是"不得新增任何 read / resolve / decrypt 通道"。两者不能同时成立。

**（四）这条新通道的安全性质与 C7 想防的东西不是一回事。** C7 防的是 **秘密材料**（明文/密文）出 main。`grantId` 不是秘密材料 —— 它是一条 **授权记录的主键**，而且它的持有者能做的唯一事情是 **撤销**（`DELETE FROM vault_grants`），即单调地 **减少** 权限。一个只能减权的标识符外泄，其最坏后果是拒绝服务（攻击者撤销用户的 grant），量级远低于 C7 的防护目标。

**（五）建议的重述**（供 CEO 裁定采纳与否）：把 C7 从"禁止一切新读通道"改为 —— **"任何 main→renderer 的返回体中不得出现明文或密文；新增读通道仅限非秘密的授权元数据（grantId / sinkKind / createdAt），且每条新通道必须与 `listDescriptors` 同样 scope-bound（`validateScopeKind` + `validateScopeId` + 精确等值）。"** 这样既保住 C7 的实质，又让 Q4-B 可交付。
