**Context (2026-07-22):** Cross-team release gate sync. Two independent reviewers (Chat Core review + a second reviewer) found that `attachStreamV4` (`use_chat_stream.js:8770-9429`, landed in `674454435b` 07-21 "harden chat recovery") can resolve `active:true, terminal:false` and then receive zero further events forever — `scheduleReplayAcceptanceReconciliation()`'s watchdog only arms `if hasUnverifiedRelayedTurn()`; a plain (non-queue-relay) reattach gets no timer at all. Verified in code: no heartbeat anywhere (`routes.py` has zero ping/heartbeat frames), no `lastUpstreamActivityAtMs` in `service.js` streamState, no idle timer in `unchain_stream_client.js`. This is the deliberate flip side of `service.js:3583-3587`'s intentional choice to drop transport-level inactivity timeouts (Node adapter has none, chosen specifically to survive Chromium sleep-suspend + Undici's 5-min quiet-body kill) — that fix is what makes the 20-min deterministic + caffeinate run pass today, and it traded away "detect truly-dead connections" to get "stop killing alive-but-silent connections."

**Decision:** NOT a blocker for 0.1.9 (target 07-27, see [[release-019-convergence]]). Confirmed the existing attachStreamV4 transport/envelope contract as sound for this release; explicitly flagged that liveness/heartbeat semantics were never part of that contract (not documented in `runtime-events-v4.md` or `request-flow-and-streaming.md`) — this is a newly-scoped gap, not a contract violation. Rationale: CEO's original ask (fix premature/false termination on sleep) is done and verified; this is the opposite failure mode (under-detection of genuinely dead links), degrades to "stuck spinner, manual cancel required" (existing `cancelCurrentStreamAndSettleMessages` escape hatch confirmed wired into chat UI) not data loss/corruption; side-menu has zero streaming-liveness indicator so background chats are worse off than foreground but still not silently corrupting anything; proper fix touches the exact file just hardened yesterday — landing under time pressure risks reopening it.

**Fast-follow spec (P1, sequence Backend → Electron → Chat Core):**
1. Backend: `routes.py`/`unchain_adapter.py` SSE generator emits `event: heartbeat` every ~15s on `/chat/stream/v4` + attach/replay path, independent of agent activity (feasible — `Agent.run()` already runs in worker thread, Flask generator polls a queue).
2. Electron: `service.js` streamState gains `lastUpstreamActivityAtMs` (updated on any received bytes), relayed to renderer.
3. Chat Core: same-identity liveness watchdog on the plain-attach path (mirrors existing `cancelAndSettleUnverifiedReattach`/`settleUnavailableStream` machinery already in `use_chat_stream.js`) — silence past ~3x heartbeat interval → exact-identity cancel via existing `enqueueExecutionCancel`/`requestExecutionCancellationAndDisconnect`, settle, **never auto-restart**.

**Consequences:** No test today covers the `active:true/terminal:false`-then-silent-forever state (confirmed absent from `use_chat_stream.js` suite) — this is a known, accepted, tracked gap, not an oversight to relitigate. Whoever picks this up next should re-verify `674454435b`'s reattach logic hasn't drifted before implementing, and must not let the new watchdog double-fire against the existing queue-relay-acceptance reconciliation path.
